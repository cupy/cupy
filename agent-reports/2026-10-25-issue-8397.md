## Root cause and implementation

PBA internally pads inputs to suitable square/cubic dimensions. Its coordinate
outputs are then cropped to the original image shape. Nevertheless,
`_check_indices` used `(arr.ndim,) + arr.shape`, where `arr` was already padded.
For a 9x9 input it demanded `(2, 32, 32)` instead of `(2, 9, 9)`. A 5x9x17
volume similarly demanded `(3, 32, 32, 32)`.

Both callers now use `(arr.ndim,) + x.shape`, where `x` is the cropped/decoded
coordinate output. This matches the shape actually assigned into the buffer,
without tracking another copy of the input shape or changing the kernels.
Integer kind/itemsize checks, return conventions, and buffer ownership remain
intact. A NumPy indices argument follows a different existing path; changing
host-array handling is outside this fix.

Changed files:

- `cupyx/scipy/ndimage/_pba_2d.py`: validate against cropped coordinate shape.
- `cupyx/scipy/ndimage/_pba_3d.py`: apply the equivalent correction after decode.
- `tests/cupyx_tests/scipy_tests/ndimage_tests/test_distance_transform.py`:
  extend in-place indices tests to aligned and padded square/rectangular shapes
  in 2D and 3D; preserve dtype, sampling, and return-distance combinations;
  assert the returned indices object is the supplied buffer; exercise invalid
  dtype/shape/options on padded inputs and reject internally padded shapes.
- This report: investigation, validation, and publication record.

No public signature, algorithm, allocation strategy, or GPU kernel was changed.
